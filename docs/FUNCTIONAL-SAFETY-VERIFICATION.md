# 控制导引与输出安全诊断验收报告

日期：2026-08-28

版本：EVSE Schematic Design 2.2 / EDEM 4.1 / ERC 1.4

结论：PASS（端子级功能合同与方案图；板级实现和施工签发仍被阻止）

## 1. 本次补齐的工程语义

- 对真实物理端子含 CP 的接口，分别建立 CP 波形发生、高阻采样和车辆二极管存在检查；GB/T 直流和 CHAdeMO 等无 CP 接口明确为 N/A，不虚构电路。
- 每个充电输出在安全接触器下游建立逐导体送电前预检，测试路径默认隔离；每个安全隔离极分别建模辅助反馈和下游电位/粘连监测。
- `ALL_OPEN → PRECHECK → READY → ENERGIZED` 是唯一允许的送电路径；任一安全故障进入 `FAULT_LATCHED` 并命令全部隔离接触器断开。
- 7 类、32 个 Qwen 来源板级拓扑只以 `CANDIDATE—ENGINEER_REVIEW_REQUIRED` 形式浏览。器件值、阈值、时序和软件判据均为 `PROJECT_VALUE_REQUIRED`，引擎不评分、不自动选型。

## 2. 可追溯实现

- `engine/functional-unit-library.js`：候选知识与可执行功能之间的单向映射。
- `engine/design-model.js`：功能单元、精确端子/网络/回路和 fail-closed 状态机。
- `engine/device-catalog.js` 与 `engine/iec-symbol-catalog.js`：5 类新增诊断设备及原生矢量符号；受控符号种类总数为 66。
- `engine/erc.js`：ERC-080 至 ERC-085，覆盖适用性、CP 唯一源/同网、下游逐导体预检、逐极反馈、状态机防旁路和引用所有权。
- SVG/DXF 仍只消费统一 Drawing IR；没有新增第二套手写坐标拓扑或手工 NETS 台账。

## 3. 自动化验收

2026-08-28 在 Windows / Node.js 24.19.0 上执行测试：

- 核心源码与元器件工作台测试 `160 / 160` 通过；同步到公开发布克隆后，连同仓库既有 `/api/ai` 代理安全测试执行 `npm test`，最终 `171 / 171` 通过，失败、跳过、取消均为 `0`；总耗时 `480.93 s`。
- 正式高密度参数矩阵 `216 / 216` 通过；发布克隆最终矩阵耗时 `474.41 s`。
- `5 接口 × 4 桩型 = 20` 个端子级模板逐一检查功能适用性和诊断覆盖。
- 20 个核心引擎模块由 `scripts/sync-web.js` 按确定顺序打入 Web bundle，并由内容哈希防分叉。

破坏变异会在重算模型哈希后再次运行语义 ERC，以下情况均 fail-closed：

- 在无 CP 接口伪造 CP 功能，或在有 CP 接口删除发生/采样/二极管检查；
- CP 功能不在同一个物理网、存在多个激励源，或不连接对应控制器；
- 预检遗漏输出导体、接到接触器上游，或测试路径没有隔离；
- 接触器反馈错误接到线圈，缺少任一安全极的反馈/粘连检测；
- 绕过 PRECHECK/READY 直接送电，故障态未全部断开，或未决阈值被伪装成可执行；
- 功能单元引用不存在、跨接口占用，或声明的 net/circuit 所有权与实际端点不一致。

## 5. 浏览器视觉验收与明确边界

在实际 Web 页面生成并检查了 GB/T 四枪直流一体、CCS2 交直流一体和 NACS 储能移动代表图。新增 CP 发生/采样/二极管检查、输出预检和逐极状态监测均使用可识别的原生符号；页面状态与模型适用性一致，无 CP 接口明确显示 N/A。

高密度四枪图虽然通过 exact coverage、几何和导出闸门，但因全部一次、二次和诊断回路仍集中在一张自定义幅面图纸上，存在大量并行长线，阅读效率尚未达到施工图要求。后续工程化必须引入多页图册、跨页连接器、母线/同网干线合并和回路索引；在此之前平台继续强制标记 `CONCEPT_DRAFT—PROFESSIONAL_REVIEW_REQUIRED`，禁止输出生产图、施工图或 IFC。

本验收不替代短路与保护配合计算、绝缘配合、EMC、温升、故障注入、接口一致性、型式试验、消防/并网审批或具备资格人员的校审签发。
